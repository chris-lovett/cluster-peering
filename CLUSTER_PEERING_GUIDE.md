# Consul Cluster Peering on Kubernetes

## Overview

Cluster peering enables secure service-to-service communication between independent Consul clusters across datacenters, cloud environments, or organizational boundaries.

**Key Benefits:**
- Multi-cloud architectures
- Cross-team service sharing
- Disaster recovery and failover
- Administrative independence per cluster

---

## What Is Cluster Peering?

Cluster peering connects independent Consul clusters for secure cross-environment communication.

**Unlike WAN Federation:**
- Clusters do not share a root Certificate Authority
- Each cluster maintains full administrative independence
- Communication requires explicit trust and policy

---

## Core Components

### 1. Peering Token
- Single-use secret generated by the accepting cluster
- Establishes trust between clusters
- Regeneration invalidates previous tokens

### 2. Mesh Gateway
- Handles all cross-cluster traffic
- Encrypts/decrypts traffic via mTLS
- Routes traffic to healthy services
- **Critical:** Requires proper WAN address configuration

### 3. Exported Services
- Services are not shared by default
- Must be explicitly exported via `ExportedServices`
- Controls visibility across clusters

### 4. Service Intentions
- Identity-based access control
- Enforced via mutual TLS
- Default behavior is deny

---

## Implementation Workflow

Complete all steps in order:

1. Install Consul on both clusters
2. Configure mesh and proxy defaults
3. Generate and exchange peering token
4. Establish peering connection
5. Export services
6. Create service intentions

---

## Prerequisites

### Environment Setup

```bash
kubectl config get-contexts

export CLUSTER1_CONTEXT=<cluster-1>
export CLUSTER2_CONTEXT=<cluster-2>
export CONSUL_VERSION=<version>
```

### Required Helm Values

```yaml
global:
  name: consul
  datacenter: dc1  # dc1 for cluster 1, dc2 for cluster 2
  peering:
    enabled: true
  tls:
    enabled: true

connectInject:
  enabled: true  # REQUIRED

meshGateway:
  enabled: true
  wanAddress:
    source: "Service"
    port: 443
```

**Critical Requirements:**
- Cluster 1 must use `dc1`
- Cluster 2 must use `dc2`
- Missing datacenter config causes: `config entry managed in different datacenter`

---

## Installation

### Install Consul on Both Clusters

```bash
# Cluster 1
helm install consul hashicorp/consul \
  --namespace consul \
  --create-namespace \
  --values values.yaml \
  --set global.datacenter=dc1 \
  --kube-context $CLUSTER1_CONTEXT

# Cluster 2
helm install consul hashicorp/consul \
  --namespace consul \
  --create-namespace \
  --values values.yaml \
  --set global.datacenter=dc2 \
  --kube-context $CLUSTER2_CONTEXT
```

---

## Configuration

### Enable Peering via Mesh Gateways

```yaml
kind: Mesh
spec:
  peering:
    peerThroughMeshGateways: true
```

### Set Local Gateway Mode

```yaml
kind: ProxyDefaults
spec:
  meshGateway:
    mode: local
```

This ensures traffic exits through the local mesh gateway, not remote.

---

## Establishing Peering

### Step 1: Create Peering Token (Cluster 1)

```yaml
kind: PeeringAcceptor
metadata:
  name: cluster-02
  namespace: consul  # REQUIRED
```

**Warning:** If namespace is missing, token is never created and peering silently fails.

### Step 2: Copy Token to Cluster 2

```bash
kubectl get secret peering-token -n consul -o yaml | \
kubectl apply -f - --context $CLUSTER2_CONTEXT
```

### Step 3: Create Dialer (Cluster 2)

```yaml
kind: PeeringDialer
metadata:
  name: cluster-01
  namespace: consul  # REQUIRED
```

### Step 4: Verify Peering

```bash
consul peering list
```

**Expected Output:**
```
State: ACTIVE
```

## Service Configuration

### Export Services

```yaml
kind: ExportedServices
spec:
  services:
  - name: backend
    consumers:
    - peer: cluster-01
```

### Create Service Intentions

```yaml
kind: ServiceIntentions
spec:
  destination:
    name: backend
  sources:
  - name: "*"
    action: deny
  - name: frontend
    action: allow
    peer: cluster-01
```

## Troubleshooting

### Common Failure: Pending State

Check in order:

1. CRDs in correct namespace
2. Token exists on both clusters
3. Mesh gateway reachable
4. WAN address is external (not internal IP)

### Critical Failure Modes

| Error | Root Cause |
|-------|------------|
| `invalid peering establishment secret` | Stale token |
| `unknown PeerID` | Corrupted state |
| `i/o timeout` | Internal IP used instead of ELB |
| `TLS handshake failed` | TLS mismatch |

### Reset Procedure

When peering fails:

1. Delete acceptor/dialer + secrets
2. Delete peering from Consul state
3. Wait 30 seconds
4. Start fresh

### WAN Address Issue (Most Common)

**Problem:** Mesh gateway advertises internal IP (`10.x.x.x`) instead of external address.

**Symptom:** Peering never connects.

**Fix:**
1. Add `meshGateway.wanAddress` to Helm values
2. Restart gateway pods

```yaml
meshGateway:
  wanAddress:
    source: "Service"
    port: 443
```

---

## Key Takeaways

- Peering is explicit, secure, and isolated
- Mesh gateways are mandatory control points
- Tokens are single-use and fragile
- Most failures stem from:
  - Namespace issues
  - WAN address misconfiguration
  - Datacenter mismatch
